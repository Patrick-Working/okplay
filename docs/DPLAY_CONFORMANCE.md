# DirectPlay conformance: clean-room dplayx that matches Windows

Started 2026-10-14. Code: this repository. Evidence tags: [V-RT] read in source, [V-SPEC] read in the published spec, [INF] reasoned, [UNV] needs a check.

## 1. Goal and what "100%" means
A `dplayx.dll` of our own, starting from Wine's (`winedplay/port/dlls/dplayx`), that behaves exactly like Windows' DirectPlay.

The code can't be byte-matched (that would mean reading Microsoft's binary). "100% match" means: **every check in the suites in section 4 gives the same result on our DLL as on Windows' DLL.** That covers the bytes on the wire (normalised for GUIDs, IDs, addresses and timestamps), API return codes and out-parameters, the system messages a game receives and their order, and interop in both directions (Windows host with our joiner, and our host with a Windows joiner).

## 2. Clean-room rules (every agent follows them)
Allowed inputs:
- Microsoft Open Specifications: [MC-DPL4CS] *DirectPlay 4 Protocol: Core and Service Providers* (rev 20.0, 2024-04-23) and [MC-DPLHP] *DirectPlay 4 Protocol: Hosting*. Their licence notice allows implementations and copying their structures and IDLs. Read online at learn.microsoft.com/openspecs. The DirectX SDK headers and docs (`scratch/dx5sdk`, `dplay.h`, `dplobby.h`, `dplaysp.h`) are public API documentation.
- Wine's source (LGPL 2.1) and our own netplay code.
- Black-box observation of Windows: calling the public API, logging what Windows' dplayx hands a service provider, and packet captures.

Forbidden: opening any Microsoft DirectPlay binary (`dplayx.dll`, `dpwsockx.dll`, `dpmodemx.dll`, `dplaysvr.exe`, `dpnet.dll`, from `DirectX/` or `C:\Windows\SysWOW64`) in Ghidra, a disassembler, a debugger, `strings`, or our Unicorn emulator. Hooking or patching their code is also forbidden. We may load them only through their public API, as any game does.

## 3. Oracle
- Windows 10 build 19041 on this PC: `C:\Windows\SysWOW64\dplayx.dll` 10.0.19041.1 and `dpwsockx.dll` are installed, so the DirectPlay feature is enabled [V-RT, file versions].
- Observed 2026-10-14 (black box: list of modules loaded into the test process, plus the test's own checks): on this PC, Windows' TCP/IP provider loads `dpnathlp.dll` (DirectPlay NAT helper). It writes the router's **public** address and a UPnP-mapped port (seen as 203.0.113.24:58057) into the SockAddr of its messages, not the LAN or loopback address. Wine's tests expect 127.0.0.1 here, so those checks fail on Windows on this PC; they are excluded from S1 by the counting rule, and each one costs a connect timeout, which makes a run slow. This belongs to the **provider (dpwsockx), not dplayx**: our `plain` dplayx on top of Windows' dpwsockx shows the same address and port. It only has to be matched when we replace the TCP/IP provider too (UPnP step in our provider) [V-RT observation; the exact rules are UNV].
- Optional later: the DirectX 5 build (4.05.00.0155, as late-1990s game discs carry it) on a Windows 98 VM: what those games shipped against [INF].

About S3's tap: Windows' dplayx loads an SP by the file name in its registry entry, so a logging SP copied as `dpwsockx.dll` next to the test program is loaded without admin rights. okplay's tests already use this "IPX slot" trick (`okplay/tests/run_local.sh`). - S0: our code touches **21 of 49** spec commands and **17 of the 17** MTM2 needs (`YOUAREDEAD` 0x18 since 2026-10-28). `PLAYERMESSAGE` 0x0A, `PACKET` 0x15 and `PLAYERWRAPPER` 0x19 are marked "check": whether MTM2 traffic causes them is not known yet.
- Gaps already known from the code [V-RT] (details in docs/NETPLAY_ARCHITECTURE.md):
  - no reliable protocol layer (`PACKET2_DATA`/`PACKET2_ACK` 0x30/0x31, `DPSESSION_DIRECTPLAYPROTOCOL`); `DPSEND_GUARANTEED` doesn't change anything on the wire;
  - no large-message splitting (`PACKET` 0x15);
  - groups only partly done (`CREATEGROUP`, `DELETEGROUP`, group name changes and shortcuts are missing; `ADDPLAYERTOGROUP` is sent but not handled);
  - no secure sessions (`CHALLENGE`, `NEGOTIATE`, `SIGNED`, `KEYEXCHANGE`, ...), no multicast server, no `VOICE`, no `CREATEPLAYERVERIFY`;
  - Wine invented a command `JUSTENVELOPE` (1000) that isn't in the spec. Windows can't understand it, so it has to go or stay internal.
  - Wine's names for several commands are guesses that disagree with the spec (8 `CREATESESSION` = spec `CREATEPLAYER`, 9 `CREATENEWPLAYER` = `CREATEGROUP`, 10 `SYSTEMMESSAGE` = `PLAYERMESSAGE`, 3 `GETNAMETABLEREPLY` = `ENUMPLAYERSREPLY`, 19 `FORWARDADDPLAYER` = `ADDFORWARDREQUEST`, 36 `FORWARDADDPLAYERNACK` = `ADDFORWARDREPLY`). Rename them to the spec's names once the tests are in place.

- **The "DirectPlay protocol" gap, measured (2026-10-14 night)**. Two different things had been merged in the old notes: (1) the reliable protocol of [MC-DPL4R] (compact frames with player indexes, sequence/serial, ACK; Windows implements no NACK and no extended flags; SAK on retries, every 24 frames, or after 50 ms and RTT/4), switched on by `DPSESSION_DIRECTPLAYPROTOCOL`; (2) messages 48/49 (`PACKET2_DATA/ACK`), the core spec's splitter for messages larger than the provider's maximum - what the AoE2 logs actually showed. Black box on Windows 10: its dplayx hosts a protocol session only with `DPSESSION_NOPRESERVEORDER` as well (0x6044/0xC044 work, 0x2044/0x2004 fail with E_FAIL); in such a session it puts **no MC-DPL4R frames on the wire** - over its TCP/IP provider and over okplay, with plain, guaranteed or async sends. What the flag does change: async sends go to the provider's `SendEx` with the async flag, two buffers (8-byte from/to + data, no header space) and a context; the provider returns E_PENDING and reports `IDirectPlaySP::SendComplete(context, hr)` later from its own thread. Done to match: our TCP/IP provider answers async SendEx/SendToGroupEx that way (completion as an APC on its thread), and reports its version from SPInit (0x60000; Windows' dplayx refused to load it with the 0 it passed in). Result: **Windows' own dplayx runs on our provider** (hosted a 0xC044 async session, Windows joiner, 55/55 completions), and S4 full is 8/8 with 0xC044 too. Left: receiving 48/49 when Windows splits a message bigger than the provider's maximum (over TCP/IP: unguaranteed > 64 KB, rare), and MC-DPL4R itself only if a case shows Windows emitting it (e.g. DirectX 6/7 on Windows 9x - the VM test is deferred).
