# Classic Netplay drop-in v0.8.0: architecture and reliability

Source studied: the Classic Netplay drop-in v0.8.0 as released (`okplay/`, `winedplay/`).
Study mode: read-only. Nothing was built, no network was used, no game was run.

Evidence tags:
- **[V-RT]** read directly from the files, with a pointer.
- **[INF]** reasoned from code that was read, not observed running.
- **[UNV]** not verifiable from this tree (live website, real Windows behaviour, real game runs).

## 0. Short answer to the key question

**Does `DPSEND_GUARANTEED` change what goes on the wire in v0.8.0? No.** [V-RT]

1. The flag does travel from the game's `IDirectPlay2A::Send` down to the service provider: `dplay.c:4264-4302` (`Send`) calls `SendEx` (`dplay.c:6047`), which copies `flags` into `DPSP_SENDEXDATA.dwFlags` (`dplay.c:6119`); `DP_SP_SendEx` (`WD/sp_compat.c:60-94`) copies it into `DPSP_SENDDATA.dwFlags` (`sp_compat.c:83`) and calls okplay's `Send` callback.
2. okplay's `OKP_Send_impl` (`OK/sp.c:205-232`) **never reads `d->dwFlags`** (it only prints it in a log line for system messages, `sp.c:228`). It calls `okp_send_data(c, to, msg, len)` (`sp.c:231`), a function that has no flags parameter (`OK/net.c:484`).
3. `okp_send_data` decides "reliable lane or plain datagram" from the **bytes**, not the flag (`net.c:491`): reliable iff the message starts with the ASCII magic `"play"` (a DirectPlay *system* message) **or** is longer than 1200 bytes. The comment at `net.c:487-490` says so explicitly: "The game's own (small) traffic stays unreliable - AoE2 recovers from loss itself."
4. The only place `DPSEND_GUARANTEED` is looked at in Wine's layer is `dplay.c:6111-6112` and `6138-6139`: it only decides whether the *SP header placeholder buffer* is included in the buffer list handed to a DirectX-6-style `SendEx`. `flatten()` (`sp_compat.c:31-52`) puts that header in front in both cases, so **the bytes handed to okplay are identical for guaranteed and non-guaranteed sends**.
5. The planned feature "reliable delivery for `DPSEND_GUARANTEED`" is listed as future step 4 in `okplay/docs/wine-dplayx-exploration.md:73` and was never done in the code (`grep` for `GUARANTEED` in `OK/` finds nothing; in `WD/` only the internal system senders use it).
6. The website sentence "The game's own traffic keeps the delivery guarantees the game asks DirectPlay for" (`winedplay/package/index.html:200`) is therefore **not backed by code in this tree** for any game (for AoE2 the claim is "true" only in the sense that AoE2 itself tolerates loss; the transport does not provide the guarantee). The live page was not read, only this template [UNV for the live page].
7. The drop-in does **not** implement DirectPlay's own guaranteed-delivery protocol layer (the `DPSESSION_DIRECTPLAYPROTOCOL` wrapper, commands 48/49 on Windows): `dplayx_main.c:26-34` says it is not implemented, `wine-dplayx-exploration.md:30-38` lists it as gap 1, `okp.h:103-109` says the drop-in "can't talk to Windows'" because there is no such wrapping, and there is no handler for those commands in `DP_HandleMessage` (`dplay.c:474-740`, `grep case DPMSGCMD_`). [V-RT]

### 1.2 How the drop-in sits between game and network [V-RT]

- **Loading.** The game imports `DPLAYX.dll` by ordinal; the exports 1,2,4 (and 3,5,6,9) are declared in `SH/dplayx.def`. `winedplay/build.sh:44-45` rewrites the def so that `DirectPlayCreate`, `DirectPlayEnumerate*`, `DirectPlayLobbyCreate*` and `DllGetClassObject` point at `MODE_*` wrappers in `SH/mode.c:241-297`, and adds the export `SPInit=SPInit@4` (`build.sh:45`) so the DLL can load itself as a service provider.
- **The "switch".** `SH/mode.c:149-232` `decide()` runs once (INIT_ONCE, `mode.c:234-237`) at the first DirectPlay call: reads `okplay.ini [okplay] mode=` (default `all`; env `OKP_MODE` overrides, `mode.c:152-158`), loads the system `dplayx.dll` by full path if the Windows DirectPlay feature is installed (`mode.c:85-121`; on Windows 9x a renamed copy `dplayx-windows9x.dll` is used), and if a lobby program launched the game (`launched_by_lobby`, `mode.c:124-135`, `lobby_auto=1`) it forces Windows' DirectPlay because only that holds the lobby connection settings.
  - `mode=all` (default): `MODE_DirectPlayCreate` (`mode.c:241-257`) returns a switcher for `GUID_NULL`, Windows' object for a non-ours GUID, Wine's object for ours. `SH/switch.c` is the switcher: it is a per-interface vtable of generated thunks that swap `this` for the target and jump to the same slot (`switch.c:44-66`, `SLOTS=53` = IDirectPlay4's vtable); only `QueryInterface/AddRef/Release`, `EnumConnections` (`switch.c:249-272`: ours first, then Windows', duplicates and Windows' view of our GUIDs removed) and `InitializeConnection` (`switch.c:275-315`: a non-ours provider GUID moves every interface the game holds to Windows' object) are real. `DirectPlayEnumerateA/W` merge the two lists the same way (`switch.c:414-438`).
  - `mode=oldkid`: Wine's dplayx only. `mode=windows`: everything forwarded to the system dplayx (exactly "as without the drop-in"). `mode=ask`: message box.
- **How providers are registered/enumerated.** No registry entry is needed. `DP_InitConnections` (`dplay.c:5312-5330`) calls `DP_BUILTIN_AddConnections` (`builtin.c:120-129`), which adds two `DPCONNECTION` entries whose `path` is the DLL's own file name and whose compound address names the GUIDs `{66D8DC59-28E8-4D3E-BA93-2E98D251C0F3}` (Online) and `{6BCFF704-CE20-4150-98B4-5A7198175D7D}` (LAN) (`builtin.c:51-52`, `okp.h:30-33`). Wine's registry reader (HKLM `Service Providers`) only runs if `show_windows_connections=1` (`dplay.c:5316-5321`), and skips okplay's own GUIDs if an old installer registered them (`dplay.c:5207-5214`). `DP_LoadSP` (`dplay.c:5557-5588`) `LoadLibraryA`s that path (= itself) and `DP_InitializeDPSP` (`dplay.c:5590-5627`) calls its exported `SPInit`.
- **How okplay is compiled into it.** `winedplay/build.sh`: Wine files `WD/*.c` + `SH/{winedbg_shim,com_exports,mode,switch,win9x}.c` are compiled with `-DOKP_BUILTIN -include okplay/src/okp_stdio.h -iquote okplay/src` (`build.sh:18-27, 34`); okplay's `sp net rdv lan util crash compat okp_printf` are compiled separately with `-DOKP_BUILTIN` (`build.sh:36-41`) and everything is linked into one `bin/dropin/dplayx.dll` with the version resource (`build.sh:42, 47-48`). The `plain` build (`build.sh:28-31`) is Wine's dplayx without okplay/mode/switch, used for Wine's conformance tests. `OKP_BUILTIN` changes few things inside okplay itself (`grep OKP_BUILTIN OK/`: `sp.c:529-578` host-migration hook `okp_became_host`, `okp_header_peer`, `okp_spdata_peer`, `okp_builtin_attach`; message boxes in `rdv.c:403,421`, `lan.c:29`, `net.c:1111`; `util.c:64,180` (ini `drop_pct` ignored); `version.h`).
- **Other hooks into Wine's code** (`grep OKP_BUILTIN WD/`): password boxes in `DP_SecureOpen` (`dplay.c:3909-3925` host, `3954-3964` join, `4012-4017`, `4075-4076`), `okpConnection` flag (`dplay.c:5737-5739`), sender identity for authorization (`dplay.c:7089-7147`, `DP_SenderOwns`), host-migration callback (`lifecycle.c:174-177`), process attach/detach (`dplayx_main.c:85-93`). Lobby: Wine's own lobby code returns `DPERR_NOTLOBBIED` when the game was not lobby-launched (`dplayx_global.c:858` etc.), which is what MTM2's startup probe expects. [V-RT]
- **Packaging.** `winedplay/package.sh` builds, strips, checks the file version is >= 5 ("AoE2 refuses to start with a dplayx that reports a pre-DirectX version", `package.sh:34-36`), copies `okindeo.dll`, fills `README.txt`/`okplay.ini` templates, zips, and regenerates `wine-dplayx-windows.patch` as `diff -ruN src port` (the pristine `src/` tree is **not** in this import, so the patch is the only upstream delta). The patch touches `builtin.c` (new), `dplay.c`, `dplay_global.h`, `dplaysp.c`, `dplayx_global.c`, `dplayx_main.c`, `dplayx_messages.[ch]`, `dplobby.c`, `host.c` (new, full), `lifecycle.c` (new, full), `name_server.c`, `sp_compat.c` (new) and the test file. `patch_close.py`, `patch_lifecycle.py`, `patch_lobby.py` are **one-shot editing scripts** ("Run once") with a hard-coded `D:\aoe2tool\...` path; they are not part of the build and `port/` is already the post-patch tree. [V-RT]
- `okplay/src/*` is also buildable as a stand-alone Windows service provider (`okplay/build.sh`, the retired "installer edition"). `winedplay/port/dlls/dpwsockx` is Wine's TCP/IP provider kept in the tree but **not built** into the drop-in (`build.sh` compiles only `port/dlls/dplayx/*.c`; the `dpwsockx.dll` name used in `okplay/build.sh:16` and `tests/run_local.sh:9` is a copy of okplay.dll placed in the IPX provider slot for tests). [V-RT]

### 1.3 Is the built-in transport the same code as `okplay/src/net.c` "v0.2"? [V-RT]

**Same file, much newer than its README.** There is no separate copy: `okplay/build.sh` (installer flavour) and `winedplay/build.sh` (drop-in flavour) compile the same `OK/net.c`. `OK/version.h:2-14` is the only thing that says 0.2.0 vs 0.8.0 (0.8.0 whenever `OKP_BUILTIN` is defined; `package.sh` reads the 0.8.0 number from it). `okplay/README.md` ("v0.2", "wire format v2") is stale text. ### 1.4 What is AoE2-specific and what is generic DirectPlay 4

Generic (works for any DirectPlay 2/3/4 game, [V-RT] unless marked):
- The whole SP interface (`OK/sp.c`), Wine's dplayx (sessions, players, groups, name table, host migration, keepalive), the matchmaker protocol, LAN discovery, NAT traversal, wire format, the reliable lane, tokens, the PHP server. `dwMaxPlayers` is whatever the game sets; the transport only limits itself to 16 remote machines (`OKP_MAX_PEERS`, `okp.h:39`) and reports `dwMaxPlayers = 65536` in `GetCaps` (`sp.c:418`).
- The application GUID is not checked by the transport: `OKP_EnumSessions` stores the joiner's requested GUID (`sp.c:160`) and `room_matches` filters cached rooms by it (`sp.c:111`); the server stores the host's opaque enum blob and does not look at the GUID (`okplay.php:124`). The session instance GUID is created by Wine at `Open(CREATE)` with `CoCreateGuid` (`dplay.c:4688`).

AoE2-specific (strings, assumptions) [V-RT]:

## 2. Message reliability: one outgoing `Send` traced to the wire

### 2.1 The path

MTM2 calls `IDirectPlay2A::Send(from, to, dwFlags, buf, len)` with `dwFlags = 1` (`DPSEND_GUARANTEED`) or `4` (bit with no meaning in this dplay.h, `dplay.h:1050-1059`; nothing in the drop-in reads it).

| Step | Code | What happens |
|---|---|---|
| 1 | `dplay.c:4264-4302` | `IDirectPlay2A/2/3/3A::Send` -> `IDirectPlayX_Send` -> `IDirectPlay4(A)Impl_Send` -> `IDirectPlayX_SendEx(from,to,flags,data,size, priority=0, timeout=0, NULL, NULL)` |
| 2 | `dplay.c:6047-6176` `IDirectPlay4Impl_SendEx` | No parameter checking (`FIXME`, 6061-6066). **Local loopback first**: `DP_QueueMessage(from,to,excludeId=from)` (6081) copies the message into the receive queue of every *other local* player addressed (`dplay.c:334-372, 374-401`). Then builds the buffer list `{SP header placeholder (NULL, dwSPHeaderSize), DPMSG_SYSMSGENVELOPE{dwPlayerFrom,dwPlayerTo}, payload}` (6091-6096). |
| 3 | `dplay.c:6101-6137` | If `to` is a player: one `DP_SP_SendEx` call with `lpSendBuffers = (flags & GUARANTEED) ? all 3 : &buffers[1]` (6111-6112), `dwFlags = flags`, `bSystemMessage = FALSE`. If `to` is a group or `DPID_ALLPLAYERS (0)` (= `DPID_SYSTEM_GROUP`, `dplay_global.h:275`, `DP_FindAnyGroup` `dplay.c:1621-1633`) it calls `DP_SP_SendToGroupEx` (6128-6165). Unknown `to` -> `DPERR_INVALIDPLAYER`. |
| 4 | `WD/sp_compat.c:60-94` `DP_SP_SendEx` | okplay registers only `Send` (no `SendEx`/`SendToGroup`, `sp.c:500-509`), so this takes the DX5 path: after a host migration `idPlayerTo==0` is rewritten to the new host's system player (67-71); the buffers are flattened into one block with a zeroed SP-header in front **in both cases** (`flatten`, 31-52); `send.dwFlags = data->dwFlags` (83); calls `OKP_Send`. |
| 4' | `sp_compat.c:96-164` `DP_SP_SendToGroupEx` | No group-send callback in okplay either, so: all-players group = **one `Send` per remote machine** (to its *system player* id; `153-158`), a real group = one `Send` per remote member. Individual failures are counted; returns an error only if *every* copy failed (163). |
| 5 | `OK/sp.c:205-232` `OKP_Send_impl` | Strips the SP header (209-210). `idPlayerTo==0` -> `host_peer` (213-214); otherwise `peer_of_player()` reads the target player's remote SP data (`pdata`: magic `OKPD` + 64-bit peer id + up to 3 candidate addresses, `okp.h:62-73`, `sp.c:196-203`) to find the 64-bit machine id. No peer -> `DPERR_INVALIDPLAYER`. **`dwFlags` is not used.** |
| 6 | `OK/net.c:484-547` `okp_send_data` | `reliable = begins with "play" || len > 1200` (491). Reliable: fragments (515-520) into the per-peer lane (`rel_send_locked`, 458-482). Not reliable: one `OKP_T_DATA` datagram: sent now if the peer has a working path, else queued (max 64 datagrams, dropped after 10 s, `net.c:13, 531-542, 1036-1042`). |
| 7 | `net.c:347-366` `raw_send` | `sendto` on the single UDP socket (optionally dropped by `OKP_DROP_PCT`, 349). |

Datagram sizes: header 32 bytes (`okp_wire`, `okp.h:78-86`), then for `DATA`: `[dwPlayerFrom][dwPlayerTo][game bytes]` for game messages, or `"play"+command+version+...` for DirectPlay system messages. The receiver decides what a datagram is by `dwMagic == "play"` (`dplaysp.c:225-230`), so a payload that arrives via the reliable lane is handled identically.

### 2.2 Which messages ride which lane [V-RT]

| Lane | What | Selector |
|---|---|---|
| **Reliable lane** (`RDATA`/`RFRAG`/`RACK`) | All DirectPlay system messages: enumeration *replies* (`OKP_Reply` -> `okp_send_data`, `sp.c:193`), request-player-id / reply, FORWARDADDPLAYER / ADDFORWARD / SUPERENUMPLAYERSREPLY / NACK (`host.c`), create/delete player & group, set player name/data, session-desc change, chat (`DPMSGCMD_*`, `dplayx_messages.h:97-132`), **PING/PINGREPLY** (`lifecycle.c:389-396`), IAMNAMESERVER. Also **any** message > 1200 bytes. | First 4 bytes of the SP payload are `"play"` (`net.c:491`) or `len > OKP_FRAG_MAX` |
| **Plain datagram** (`DATA`, type 3) | Every application message the game sends, small enough, regardless of `DPSEND_GUARANTEED`. Also the application-level traffic of `SendChatMessage`? No: DirectPlay chat is a system message (`DPMSGCMD_CHAT`, `dplay.c:7306-7360`) so it is reliable. | everything else |
| Not carried by the SP | Local loopback to other local players (`dplay.c:6081`), `GetPlayerData` of local players, etc. | |

`DPSEND_GUARANTEED` is attached to system messages inside Wine's code too (`lifecycle.c:83`, `host.c:163`, `dplayx_messages.c:258,611,839,882,962`) but it again does not matter: okplay keys on `"play"`, so the pings (sent with flags 0, `lifecycle.c:395`) are reliable too.

### 2.3 The reliable lane in detail [V-RT, `OK/net.c`, `OK/okp.h`]

- **Scope**: one lane per remote *machine* (peer), not per player and not per message class. Sequence numbers are 32-bit, start at 0 per peer (`rel_send_locked`, 464; `lane_restart`, 412-421, resets both ends when the other side's epoch changes).
- **Packets**: `RDATA`(6) body = `u32 seq` + payload; `RFRAG`(8) the same for non-final pieces; the final piece of a fragmented message is an `RDATA` (`net.c:515-520`). `RACK`(7) body = `u32 cumulative-next` + `u32 seq-just-received` (`net.c:821-831, 873-877`): the sender drops every unacked entry below `cum` or equal to `seq` (selective ack).
- **Fragmentation**: payload per datagram 1200 bytes (`OKP_FRAG_MAX`, `okp.h:122`); max message 65536 (`OKP_MSG_MAX`, `okp.h:124`; larger -> `okp_send_data` returns 0 -> `DPERR_GENERIC`, `net.c:486`); reassembly buffer grows by `realloc`, discarded with a log line if it would exceed the cap (`net.c:650-696`). All pieces of one message are queued under one lock so nothing interleaves (`net.c:514-520`). `GetCaps` advertises `dwMaxBufferSize = 16384` so that Windows' own splitter (broken for big player lists) is not used (`okp.h:115-123`, `sp.c:416`); Wine's dplay has no splitter at all and does not enforce the cap (no size check in `SendEx`).
- **Send window**: 128 unacked pieces per peer (`OKP_RTX_MAX`, `okp.h:126`). If a new message would not fit, it is **dropped** with a log line and `okp_send_data` returns 0 (`net.c:508-512`), `r_giveup++`.
- **Retransmit timer** (`net.c:1000-1034`, run from the net thread's 20 ms select loop, `net.c:1058`): first resend after **40 ms** (`tries==1`), then `rto = max(150 ms, 2*rtt+50 ms)` growing x1.5 per try, capped at **1 s**. RTT comes from probe acks (`net.c:804`). Resending only happens while a path exists (`p->have_path`, 1023).
- **Give-up**: an entry older than **30 s** since its first send is freed, logged ("gave up on reliable seq ..."), `r_giveup++` (`net.c:1010-1018`). Its sequence number is **not** skipped on the other side (see "stalled stream").
- **Receiver**: in-order delivery. `seq == r_rx_next` -> deliver and then drain buffered later pieces (`net.c:839-854`); `0 < seq - r_rx_next < 4096` -> buffer if not already buffered and fewer than 128 buffered (`855-869`); older -> counted as duplicate and re-acked (`870-871`). Every received RDATA/RFRAG is acked (873-877). Delivery to dplayx happens on the net thread after the lock is released (`896-907`).
- **Duplicates / ordering on the plain lane**: none. `OKP_T_DATA` is delivered immediately on arrival (`net.c:880-896`): reordering and network duplication reach the game; a duplicate of a datagram is simply queued twice.
- **Ordering between lanes**: none. A system message waiting for a retransmit does not hold back a following `DATA` datagram and vice versa.
- **Stalled stream** (README states it, `okplay/README.md` security section; confirmed in code): when the sender gives up on seq N it has already consumed N; the receiver still waits for N, buffers up to 128 later pieces and then silently drops further ones (`859-869`: not stored) **while still acking them individually** (873-877), so the sender frees them. After a give-up the lane delivers nothing more until the peer object is recreated (new epoch, `770-780`), i.e. until the peer is forgotten (`973-979`) or restarts. In practice DirectPlay removes the machine first: `lifecycle.c:41-42, 354-405` pings every machine every 1.5 s and declares it dead after 15 s without *any* message (any game or system message counts, `DP_LIFE_Heard`, `lifecycle.c:127-135`, `dplay.c:763`), then `DP_LIFE_MachineGone` -> `DP_RemovePlayer` -> `OKP_DeletePlayer` -> `keep_until = now+5 s` -> `peer forgotten` (`sp.c:288-310`, `net.c:973-979`). This needs `DPSESSION_KEEPALIVE` (MTM2 sets 0x40). One-way breakage (they hear us, we do not hear them) keeps `lastHeard` fresh on the side that still receives, so the stall can persist there. [INF]
- **Path liveness** (transport level, independent of DirectPlay): a probe every 2 s on a working path (`KEEPALIVE_MS`), path declared dead after 15 s without any trusted packet from it (`PATH_DEAD_MS`), then re-probing all candidates every 200 ms for 30 s and every 2 s afterwards (`net.c:8-14, 965-998`); a never-joined peer stops being probed after 15 s (984).

### 2.4 Other questions from the task

- **`dwMaxBufferSize` / fragmentation**: see above. Application messages of MTM2 are all far below 1200 bytes, so they never fragment; the only ones that can would be radio voice chunks `0x89` (size unmeasured, `DIRECTPLAY_USAGE.md` section 6 [UNV]).
- **SendToGroup / all-players sends**: each remote machine gets its own copy as a separate `Send` (`sp_compat.c:146-158`); a guaranteed message in that fan-out would be N-1 independent best-effort datagrams (today) or N-1 messages on N-1 reliable lanes (after the section 4.5 patch). The receiving machine fans it out to its local players (`DP_QueueMessage(toId=0)`, `dplay.c:767`, `DP_QueuePlayerMessage` skips system players, 343-344).
- **Unreachable peer**: a DATA datagram to a peer without a path is queued up to 64 packets / 10 s and then dropped silently (`net.c:531-542, 1036-1042`), `Send` still returns `DP_OK`. A reliable message is kept for 30 s, then abandoned (stall above). `Send` to an unknown player id returns `DPERR_INVALIDPLAYER`; peer table full -> `DPERR_GENERIC` (`net.c:543`). MTM2 ignores `Send`'s return value (`DIRECTPLAY_USAGE.md` 4.7).
- **Host migration** [V-RT]: only with `DPSESSION_MIGRATEHOST` (0x04): when the host machine is declared gone (said goodbye or 15 s silence), every machine independently picks the remaining *system player with the lowest DPID* (`lifecycle.c:184-203`); that machine gets `DPSYS_HOST` queued (`lifecycle.c:164`) and broadcasts `IAMNAMESERVER` (53) (`166-172`, receivers accept it only if the old host is really gone and the sender owns the id, `267-294`); it then calls `okp_became_host` so the room is announced under the new peer id with the same room number (`sp.c:537-552`). Without the flag: `DPSYS_SESSIONLOST` (`lifecycle.c:189-193`). Windows takes ~14.5 s to notice, the port 15 s (`lifecycle.c:42`).
- **Keep-alive**: the DirectPlay one above plus the transport probes; neither is related to MTM2's own 0x84/0x85 ping. A player whose game crashes disappears after about 15 s (README.txt "GOOD TO KNOW").

## 3. Connection flow

### 3.1 Session announce and enumeration (Online Play) [V-RT]

1. Host `Open(CREATE)` -> `OKP_Open_impl` (`sp.c:326-344`): `reset_session`, wait up to 1.5 s for the STUN answer (`wait_srflx`), pick `room = rand32|1`, `tok = rand64` (host proof), `is_host=1`, wake the rdv thread. (Before that Wine already created the session description with a fresh instance GUID, `dplay.c:4688`, and possibly showed the host-password box, `dplay.c:3909-3925`.)
2. The rdv thread (`rdv.c:662-720`) every `announce_ms/2` (500 ms) injects a synthetic ENUMSESSIONSREQUEST into its own dplayx (`okp_self_probe`, `sp.c:56-76`); Wine answers through the SP's `Reply` callback and okplay keeps that reply as `enum_blob` (`sp.c:172-186, 78-97`). Every `announce_ms` (1000 ms; 3000 on Windows 9x plain HTTP) it POSTs `a=announce room peer tok cands enum(b64 of the reply, <= 1024 bytes) name players maxp flags ver wire` (`rdv.c:575-606`). The server (`okplay/server/okplay.php`) keeps rooms in a flat file, TTL 15 s (`:44`), max 200 rooms / 4 per IP (`:46-47`); the answer is `ok <ip>` + `latest <ver> <note>` + one `knock <peer> <cands>` line per waiting joiner (`:135-138`).
3. Joiner: the game's `EnumSessions` (MTM2: synchronous, 1000 ms, `DPENUMSESSIONS_AVAILABLE`) calls `OKP_EnumSessions_impl` (`sp.c:145-170`): note the request's application GUID and flags, wake the rdv thread, **answer immediately from the last cached listing** by feeding each cached host reply into `HandleMessage` (`okp_inject_rooms`, `sp.c:119-141`; only rooms that pass `okp_enum_blob_ok`, wire version, application GUID and the AVAILABLE filter). The rdv thread refreshes with `a=list` at most once per second (`rdv.c:710-714`, `parse_list` 505-536). Consequence: the very first poll after the provider is chosen is empty; MTM2 re-polls on a timer so rooms appear on the next one. [INF]
4. LAN Play instead broadcasts `OKP_T_LAN_DISCOVER` (`"OKLN"`) on UDP 47632 to every interface's directed broadcast plus 255.255.255.255 and 127.0.0.1 (`lan.c:76-131, 143-169`); a hosting machine bound to that port answers each LAN-source discover with an `OKP_T_LAN_OFFER` carrying its enum blob and up to 6 candidates (`lan.c:171-210, 133-141, 289-291`); rooms expire 6 s after the last offer (`okp.h:30`, `sp.c:130`).

### 3.2 Join handshake [V-RT]

`Open(JOIN)` (`sp.c:346-381`): take room/host from the SP header of the enumerated reply, add the host's candidates to its peer entry, then (Online) POST `a=knock` every 3 s for up to 10 s while waiting for any path to the host (`okp_wait_path`, `net.c:549-561`); failure -> `DPERR_NOCONNECTION`. Once a path exists Wine runs the (now reliable) DirectPlay join: `REQUESTNEWPLAYERID` -> `NEWPLAYERIDREPLY` (waits up to 30 s, `dplayx_messages.c:269`, `DPMSG_DEFAULT_WAIT_TIME`) -> `FORWARDADDPLAYER` with the password hash (waits up to 60 s, `dplayx_messages.c:621-622`) -> the host replies `SUPERENUMPLAYERSREPLY` (session desc, all players with their SP data) or `FORWARDADDPLAYERNACK` (`host.c:174-326`) and sends `ADDFORWARD` to every other machine (`host.c:139-172`). Afterwards the game's `CreatePlayer` produces `CREATESESSION/CREATENEWPLAYER` style messages to everyone (`dplayx_messages.c:839-974`). Every one of these starts with `"play"`, so they ride the reliable lane; that is exactly why the lane exists (Windows' dplayx did not resend its join handshake over an unreliable SP, README).

### 3.3 NAT traversal sequence [V-RT]

1. Candidates (`net.c:229-311`): srflx address first (from STUN, else server-seen IP + local port "guess", else the address a peer reports in a probe ack), then local IPv4 addresses (169.254 only in LAN mode, loopback never online), then at most two global (2000::/3) preferred IPv6 addresses (stable before temporary). Max 8 per peer, 3 are embedded in player data (`OKP_PDATA_CANDS`), 6 in LAN offers.
2. STUN (`net.c:567-641, 944-954`): Binding Request (RFC 5389, magic cookie) sent in parallel to the configured servers, up to 4 tries 700 ms apart; XOR-MAPPED-ADDRESS (IPv4 only). Servers from `okplay.ini stun=` (default Cloudflare, Google x2, Nextcloud:443, `util.c:177-178`).
3. Both sides probe all candidates of the other: host learns the joiner's candidates from the server "knock" (`rdv.c:479-502`), joiner knows the host's from the listing; probes every 200 ms for 30 s then every 2 s (`net.c:981-994`). `OKP_T_PROBE` body = `nonce, t_send, epoch, token`; `OKP_T_PROBE_ACK` echoes nonce/time and the observed source address, plus the acker's token (`okp.h:87-102`, `net.c:744-787, 801-820`). The first trusted answer from an address becomes the path (`set_path`, `net.c:434-454`, sticky while alive for 5 s) and flushes queued datagrams.
4. IPv6 needs nothing special (dual-stack socket, `IPV6_V6ONLY=0`, `net.c:1119-1121`); no relay exists, so symmetric-NAT <-> port-restricted or symmetric <-> symmetric fails (`natsim`/`nat_matrix.py` `EXPECT_FAIL`).

### 3.4 Wire format, identity, security [V-RT]

- All packets are little-endian packed structs (`okp.h:76-102`): `okp_wire` = `'O','K', ver(=4), type, room u32, from u64, to u64, token u64` (32 bytes). Types: 1 PROBE, 2 PROBE_ACK, 3 DATA, 4 LAN_DISCOVER, 5 LAN_OFFER, 6 RDATA, 7 RACK, 8 RFRAG (`okp.h:111-117`). Unknown types from a trusted peer are ignored (they fall through the `if` chain in `handle_packet`), which makes new control types backwards compatible.
- Version policy: a packet with another `ver` is dropped silently (`net.c:726`); the server list carries each room's `wire` and joiners hide incompatible rooms (`rdv.c:515-520`). A packet for another `room` is dropped (`net.c:728`).
- Identity: peers are random 64-bit ids chosen at `SPInit` (`sp.c:492`), carried in the wire header and in the replicated SP player data (`OKPD`), never IP addresses; ids of players are DirectPlay DPIDs, mapped to a peer through that SP data (`sp.c:196-203`). `DP_SenderOwns` (`dplay.c:7121-7147`) binds system messages to the machine whose SP header peer owns the named player (host-left, I-am-host, delete-player, name/data/desc changes, chat, ping replies).
- Tokens (wire 4): each side invents a token per peer (`net.c:55`), tells it in probes/acks only to addresses it already trusts, and drops any non-probe packet that does not carry it (`net.c:742, 789-796`). Cheap spoofing protection for on-path observers it is not (everything is clear text), but off-path forging of game or control packets is blocked.
- Passwords: `okp1-` + first 20 bytes (40 hex chars) of SHA-256(`"okplay game password v1|"` + UTF-8 text + the session's instance GUID) (`builtin.c:211-233`); the host stores the hash in `DPSESSIONDESC2.lpszPassword`, the joiner sends the same hash, and `host.c:220` compares them as strings. The hash is the password equivalent for that one game and travels unencrypted.
- Hardening: all parsers bounds-checked and fuzzed with a guard-page harness (`okplay/tests/fuzz.c`), probe target filtering (`net.c:63-82`), room/knock limits on the server, LAN replies only to LAN sources, `rogue_check.py` negative control for the sender-ownership check (`winedplay/build.sh:51-62`).
